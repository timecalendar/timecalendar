## Context

TimeCalendar's native contract is iPhone and iPad support in portrait-only, full-screen mode with iPad multitasking disabled; Android portrait tablets are also a responsive-layout target. The current UI already has useful pieces: `Spacing` tokens, a single `MaxContentWidth = 800`, safe-area-aware screens, native Stack/native-tabs chrome behind owned seams, and feature-local presentational tests. The audit found three recurring gaps:

1. `MaxContentWidth` is used both for prose/forms and for denser lists, so readable content can still become too wide.
2. A few screens remain uncapped, while Home timeline geometry reads the global window even though Home itself is capped.
3. Each screen makes local width decisions, leaving no shared breakpoint semantics or repeatable phone/tablet proof.

The exact Expo SDK 56 references support the existing direction: Expo Router's Stack owns native `formSheet` and detent options, native-tabs has platform-specific inset behavior, and Expo UI Host exposes content-layout measurement. The implementation must retain the repository's own chrome and safe-area seams rather than importing around them:

- `https://docs.expo.dev/versions/v56.0.0/sdk/router/`
- `https://docs.expo.dev/versions/v56.0.0/sdk/router/native-tabs/`
- `https://docs.expo.dev/versions/v56.0.0/sdk/ui/universal/host/`
- `https://docs.expo.dev/develop/user-interface/safe-areas/`

## Goals / Non-Goals

**Goals:**

- Give every route an implementation-grade tablet disposition, including explicit no-change outcomes.
- Make width decisions from the actual laid-out container and keep breakpoint behavior testable as pure logic.
- Distinguish readable, standard, and full-bleed surfaces without a new dependency or device-name checks.
- Preserve native chrome, safe areas, keyboard behavior, accessibility reading order, and phone layouts.

**Non-Goals:**

- Landscape, iPad multitasking, split view, sidebars, multi-window behavior, or changes to native device/orientation configuration.
- Business/data behavior, route flow, API/schema/generated-client changes, or legacy Flutter work.
- A wholesale redesign, speculative master-detail navigation, new navigation APIs, or screenshot/physical-device approval gates.

## Decision 1 — Measure the laid-out container and derive one semantic mode

Create a small shared layout primitive/hook that receives width from React Native `onLayout` at the surface that owns the usable content area. Its pure resolver returns `compact` below 600 points and `tablet` at 600 points or above. Components may use `useWindowDimensions` only for truly window-owned overlays; nested content, capped parents, and form sheets use their own measured width.

The resolver exposes the measured width and mode, not device type or model. It keeps the initial render compact until a positive layout width is known, which avoids tablet-only structure flashing on phones and makes tests deterministic.

_Alternative rejected_: global `Dimensions` or device/tablet detection. It cannot describe nested/form-sheet width and scatters platform assumptions.

## Decision 2 — Three width lanes, one gutter rule

The shared contract has three semantic lanes:

- **Readable**: forms, prose, metadata, status/empty/error content; cap at 640 points.
- **Standard**: grouped lists, cards, and management surfaces; retain the existing 800-point maximum.
- **Full bleed**: information-dense or camera/rendering surfaces whose geometry benefits from all available width; no maximum.

All lanes align within the existing safe-area/chrome boundary. Horizontal gutters are `Spacing.four` in compact mode and `Spacing.six` in tablet mode; a lane's usable width is the measured container minus both gutters and then its semantic cap. No screen adds a second safe-area inset or hard-coded device-specific margin.

_Alternative rejected_: replace every screen with one larger max width. It either stretches prose/forms or wastes the calendar canvas and does not encode intent.

## Decision 3 — Extra space is earned by content, not by tablet detection alone

Calendar day/week geometry and the QR camera remain full bleed. Standard/readable screens stay centered. An adaptive two-column composition is allowed only at measured widths of 834 points or greater, only when both columns are independent scan groups, and only when DOM/accessibility order remains meaningful as a single top-to-bottom sequence. At 768 points, surfaces use the tablet gutter and lane cap without forcing columns.

Home may place Upcoming and Today summary content in a deliberate wide composition at 834+ while keeping the welcome block full-row. Settings/About may place whole independent sections into columns at 834+; rows and forms do not stretch individually. Event details may pair metadata with checklist content at 834+ if the reading/focus order remains title → metadata → actions → checklist. Forms remain one readable column at every supported portrait width.

_Alternative rejected_: a universal tablet grid. It adds churn to simple screens, risks accessibility-order regressions, and makes 768-point portrait layouts cramped.

## Decision 4 — Preserve native presentation and chrome ownership

Expo Router Stack and the existing chrome seam remain authoritative. The changelog keeps iOS `formSheet` and Android `fullScreenModal`; responsive work constrains the sheet's inner readable content and does not introduce custom modal sizing. Native tabs stay behind `@/components/chrome`, and screen content continues to respect the platform-specific inset behavior already encoded there. Menus, alerts, date/time pickers, header actions, FABs, and back behavior keep their platform idioms.

_Alternative rejected_: custom tablet modals, sidebars, or replacing native tabs. Those are product/navigation redesigns, not quick wins.

## Decision 6 — File ownership and merge order

Implementation order is TIM-499 foundation, then TIM-500/TIM-501/TIM-502, then TIM-503 integration. The foundation owns shared responsive resolver/primitives, theme exports, shell alignment, Architecture Book contract, and their tests. Feature workstreams consume those APIs and do not create competing breakpoints or shared containers.

Cross-workstream files have a single writer:

- `mobile/src/features/calendar-sources/ui/user-calendars-screen.tsx` and rename-dialog layout: TIM-501; TIM-502 verifies only the Settings entry and integrated behavior.
- `mobile/src/app/_layout.tsx` and `mobile/src/components/chrome/**`: TIM-499 if changes prove necessary; later workstreams request/use the established shell and avoid edits.
- `mobile/src/theme/**` and shared responsive components/tests: TIM-499; feature workstreams add no local tablet constants.
- `docs/mobile/tablet-quick-wins.md`: TIM-499 records actual foundation decisions, each feature owner updates its rows after implementation, and TIM-503 reconciles final evidence.

Each downstream branch starts from the merged predecessor required by its blocker. If two workstreams need the same non-owned file, the later one rebases and makes the narrow integration edit after the owner merges.

## Decision 7 — Verification is layered and does not create a human gate

The pure resolver is table-tested at 390, 599, 600, 768, 800, 834, and 1024. Shared lane components are tested with reported container widths, including a nested width smaller than the window. Each changed screen gets focused component assertions for compact/tablet structure and its loading/empty/error/dense states. Static route tests preserve native presentation and redirects. Existing Maestro flows remain selector-valid; no new business journey is introduced.

Local proof is formatting, TypeScript, lint, focused Jest, and the repository's existing static Maestro validation. TIM-503 performs the full mobile regression and records simulator/emulator evidence when available, but screenshots, physical devices, and subjective review are not merge gates.

## Risks / Trade-offs

- [A shared primitive becomes an all-purpose layout framework] → keep only measurement, lane, gutter, and resolver behavior; feature composition stays feature-owned.
- [Columns reorder screen-reader focus or collapse under large text] → permit columns only for independent groups at 834+, preserve source order, and fall back to one column under width/font stress.
- [Window width leaks into nested/capped content] → tests report a container width that deliberately differs from window width.
- [Parallel work edits shared files] → enforce Decision 6 ownership and merge order; TIM-503 resolves only final integration drift.
- [Calendar density changes behavior or gestures] → keep data/controller/event semantics untouched and verify existing gesture/tile tests alongside width assertions.
- [Native safe areas or modal behavior regress] → keep existing Stack/native-tabs/chrome ownership and change inner content only.

## Migration Plan

This is an additive UI refactor with no persisted-data or server migration. Land the shared contract first, migrate bounded feature groups, then run the full-route reconciliation. Rollback is a normal revert of UI commits; no data or native shell remains to unwind.

## Open Questions

None blocking. Optional 834+ columns must earn their inclusion in each feature test; when they do not improve scanability or preserve accessibility order, the matrix's centered single-column fallback is the required outcome.
