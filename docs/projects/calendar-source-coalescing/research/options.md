# Architectural comparison

All options must preserve P01–P03. “Exact identity” means D01: strategy/version, effective
URL including credential-bearing components, effective fetcher configuration and auth
isolation. All share bytes only unless explicitly described as a rejected broader model.

| Concern | A: process single-flight only | B: Redis flight + short result cache | C: source-keyed queue jobs, no source table | D: persistent calendar_source model | E: staged hybrid |
| --- | --- | --- | --- | --- | --- |
| Correctness | One overlapping promise per exact key; no reuse after completion. | Expiring validated bytes; lease owner fenced on publication; duplicate fetch possible on failover. | Deduplicate download job, then separately apply results to each calendar; membership races need resolution. | Durable source revision plus per-calendar application cursor; extensive consistency design. | Shadow first, then B; optional process map only if it removes measured Redis load. |
| Authentication isolation | Exact identity; bypass unsupported auth. | Exact identity; bypass custom auth until cleanup proven; no credential-less key. | Exact identity in job ID digest; never lose auth context during fanout. | Unique source identity includes auth context; rotation must detach/rekey safely. | Same as B at every stage. |
| URL transformations | Resolve before map lookup; date windows separate. | Resolve before Redis lookup; no extra canonicalization. | Resolve before enqueue and validate against current calendar on apply. | Persist effective identity/revision separately from stored user URL; refresh derived windows. | Shadow and live must use identical transformation and identity code. |
| Strategy-version invalidation | New key; old flights drain. | Versioned namespace, absolute TTL; mixed pods cannot reuse incompatible versions. | Versioned job/result IDs; drain obsolete jobs without blocking replacements. | Versioned rows/revisions; reprocess affected memberships. | B semantics; disable incompatible cohorts during version rollout. |
| Failure isolation | Shared attempt failure, independent per-calendar error handling; rejected promise removed. | No negative cache; failed owner publishes nothing; follower recovery bounded. | Retry shared fetch separately from independent calendar apply; queue stalls delay all members. | Source outage affects members; apply failure must not roll back source or peers. | Measure first; same bounded failure scope as B in live mode. |
| Transaction boundaries | Download before each calendar transaction. | No Redis operation inside content/log transaction; no cross-system commit. | Fetch result durable enough for fanout; each apply transaction separate; acknowledgement races. | Source commit and calendar commits separate with idempotent revision application. | Existing content/log atomicity retained throughout. |
| Multi-pod | No cross-pod savings. | Shared keys/leases; best-effort suppression, not exactly-once transport. | Shared queue deduplication; worker crashes and stalled jobs can repeat requests. | DB uniqueness plus scheduler lease; durable model alone does not prevent concurrent fetching. | B after shadow validates replica-safe metrics. |
| Privacy | Transient response/promise in process; no new external data store. | Short-lived calendar bytes in Redis; bounded retention and access; opaque keys. | Bytes and source identity can remain in queue payload/results; retention is explicit. | Long-lived source catalog and membership graph increase sensitive-data footprint. | Shadow stores only digests/timestamps; live adds B's bounded bytes. |
| Database cost | Unchanged per-calendar writes. | Unchanged per-calendar writes; no schema/index/backfill. | No source table; membership discovery or ephemeral fanout set still costs work. | Table/index/storage, membership and revision writes, backfill and cleanup. | No schema changes; reduced HTTP does not imply reduced calendar writes. |
| Redis cost | None. | Lookup/lock/publish/read operations, bytes × live distinct keys plus metadata. | BullMQ jobs, dedup keys, fanout/results and retention; queue competes with existing sync. | Optional locks/cache; DB becomes the durable cost center. | Timestamp-only shadow first; B has hard admission limits. |
| Operational failure modes | Process restart loses flights; memory/waiter growth; cancellation coupling. | Outage, eviction, lease expiry, oversized payloads and stale owners; bounded fail-open. | Backlog, job-ID retention preventing fresh work, orphan fanout, retry storms. | Migration/backfill races, orphan sources, revision drift, scheduler ownership. | Extra flag/mode combinations; kill switch must cover all sharing paths. |
| Observability | Local joins, wait, failures, actual attempts; cannot infer global savings. | Demand/hit/join/fallback counts, actual attempts, reuse age, sizes, Redis occupancy and latency. | Queue delay, fetch jobs versus apply jobs, retry/fanout completeness and actual HTTP. | Source fetch/revision lag, membership coverage, per-calendar apply lag and HTTP. | Comparable shadow/bypass/live cohorts, bounded labels and per-trigger measurement. |
| Migration needs | No data migration; new in-memory download seam. | No data migration; download seam, strategy version and Redis client/config. | New job identity and fanout flow; drain existing calendar jobs safely. | Schema migration, source backfill, dual-read/write or cutover validation. | No DB migration; prerequisites and evidence gates precede live use. |
| Rollout / rollback | Feature flag; remove map to bypass. | Shadow → allowlist → measured expansion; disable sharing, drain flights, let TTL expire. | Route flags, stop source enqueue, drain/reconcile fanout before reverting. | Dual model rollback; preserve memberships and revision state; costly after cutover. | Stop at any gate; B rollback with independent shadow toggle. |

## Recommendation and rejected alternatives

Choose E as the delivery method and B as the initial live architecture. Do not add a local
map until measured contention justifies another lifetime/cancellation layer. A is attractive
for simplicity but misses cross-pod and spread-out on-access demand. C is a mismatch for
interactive/create traffic and introduces fanout coordination merely to save downloads.
D is justified only by a future product need for durable source ownership or centralized
scheduling, which the owner explicitly excludes initially. Doing nothing remains preferable
if bounded caching cannot deliver meaningful savings safely.
