# 5 — Security and operations

## 5.1 Threat model

A self-hosted runner executes repository code with the permissions of its operating-system account.
Unlike a GitHub-hosted runner, the machine is not recreated after each job. The threats are:

- malicious or compromised pull-request code;
- a dependency install or native build script reading host data;
- poisoned caches affecting later trusted jobs;
- one job observing another job's processes or files;
- leaked GitHub, Expo, Apple, Google, SSH or cloud credentials;
- home LAN or production-network reachability increasing blast radius;
- stale macOS/Xcode/runner software;
- physical, power, disk and ISP failure.

GitHub explicitly warns that persistent self-hosted runners lack a clean-machine guarantee and can
remain compromised. The design controls exposure instead of pretending persistence is isolation.

Source: [GitHub secure use reference](https://docs.github.com/en/actions/reference/security/secure-use).

## 5.2 Host hardening baseline

Before registration:

- dedicate the Mac to CI; do not use it as a personal desktop;
- enable FileVault and retain the recovery key outside the machine;
- create a standard, non-admin `timecalendar-runner` account;
- no iCloud login, mail, browser profile, personal SSH key or password manager in that account;
- enable the macOS firewall; expose no public inbound service;
- disable automatic login and screen sharing;
- configure restart after power failure and prevent sleep while on AC power;
- keep macOS security updates current, but schedule Xcode upgrades rather than accepting them
  mid-run;
- use a small UPS if the machine will become a regular CI dependency;
- limit Tailscale SSH to named human operators; the GitHub runner itself only needs outbound access;
- document physical owner, reboot procedure and recovery location.

## 5.3 GitHub runner controls

- repository-level registration for a dedicated **private orchestration repository** only;
- no registration, runner-group access or self-hosted label exposed to public
  `timecalendar/timecalendar` workflows;
- one runner listener and one job at a time;
- protect the private repository's default branch and restrict its writers;
- workflow permissions default to read-only contents;
- pin third-party actions to reviewed immutable SHAs in the later implementation;
- no public-repository event or workflow definition executes directly on the Mac;
- no workflow input capable of becoming a command;
- restrict manual dispatch to repository collaborators;
- mint the public-to-private dispatch token from a GitHub App whose key is held in an environment
  whose deployment-branch policy permits only `main`; scope the app to the one destination and make
  it unavailable to pull-request workflows;
- use concurrency so stale queued `main` runs are cancelled;
- subscribe to `actions/runner` release notices and verify runner auto-update health;
- log runner name, version and labels in every job summary.

Do not rely on GitHub Environment approval to make an otherwise hostile self-hosted job safe. GitHub
notes that environment secrets still execute on the same non-isolated machine after approval.

## 5.4 Secret placement

| Secret/material                        | Mac Mini                                          | GitHub environment                         | EAS/store service               |
| -------------------------------------- | ------------------------------------------------- | ------------------------------------------ | ------------------------------- |
| GitHub runner registration token       | bootstrap only; not retained as a workflow secret | generated by GitHub                        | n/a                             |
| Per-job `GITHUB_TOKEN`                 | short-lived, read-only where possible             | issued by GitHub                           | n/a                             |
| Expo automation token                  | **no** for E2E                                    | submit job only if required                | Expo account                    |
| Apple distribution certificate/profile | **no**                                            | no raw copy                                | EAS-managed credentials / Apple |
| App Store Connect API key              | **no**                                            | submit environment only if EAS requires it | App Store Connect/EAS           |
| Google Play service account key        | **no**                                            | submit environment only if required        | EAS/Google Play                 |
| Firebase production service account    | **no**                                            | not needed                                 | existing production systems     |
| E2E Firebase material                  | generated throwaway by existing harness           | none                                       | n/a                             |

Never cache a secret. Never print an environment dump. Never store a credential in a simulator,
DerivedData, Gradle cache or artifact.

## 5.5 Store and deploy gates

Building unsigned simulator artifacts is verification. Uploading an IPA/AAB to TestFlight or Play
changes an external system and is a deploy act.

Use separate source-repository GitHub environments for EAS submission jobs:

- `mobile-internal-submit`;
- `mobile-beta-submit`;
- `mobile-production-submit`.

Each submission job receives secrets only after its environment protection rule passes. Production
prevents self-approval and accepts protected release tags only. Environment approval does not
authorize Terraform, Kubernetes, OTA promotion or store rollout; those remain their own acts.

GitHub environment protection and secret timing are documented in
[Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

## 5.6 Operational checks

### Per job

- verify disk has headroom;
- verify pinned Xcode, simulator runtime, Node, JDK, CocoaPods and Maestro versions;
- verify no previous runner job is active;
- resolve SHA and use trusted workflow definition;
- start/stop the existing native E2E server lifecycle;
- capture timing and failure evidence;
- clean repository worktree and ephemeral test state.

### Weekly

- run one clean-cache iOS E2E;
- check disk/cache quotas;
- review runner update status and failed-job classifications;
- exercise or at least inspect the hosted fallback workflow;
- confirm no secret-bearing workflow has targeted Mac labels.

### Monthly

- patch macOS security updates in a window;
- review Xcode support against Expo SDK and App Store requirements;
- rotate/remove stale runner registrations;
- review GitHub collaborators who can dispatch workflows;
- verify FileVault, firewall, sleep and power-recovery settings;
- review p50/p90 performance and availability.

## 5.7 Incident response

Treat these as compromise signals: an unexpected process, changed runner files, cache-owned build
differences, secret access in an E2E job, unexplained outbound traffic or a job from an untrusted ref.

Response:

1. remove/disable the runner in GitHub;
2. use hosted fallback for required verification;
3. revoke runner registration and any token that could have reached the host;
4. preserve relevant logs without copying credentials;
5. erase/rebuild the runner account or host—do not "clean a few files" and trust it again;
6. rotate any secret whose exposure cannot be disproved;
7. re-register with a new runner identity;
8. run clean-cache verification before restoring normal routing.

The build pipeline must remain usable while this happens. That is why hosted fallback is part of the
architecture, not an afterthought.

## 5.8 Machine readiness inventory

The implementation owner records, without secrets:

- Mac model/chip, cores and RAM;
- internal SSD size and free space;
- macOS build and FileVault/firewall state;
- Xcode build and installed simulator runtimes;
- Node from `.nvmrc`, JDK 17, Ruby/Fastlane only if actually needed, CocoaPods and Maestro 2.8.0;
- Android SDK/emulator availability for the later experiment;
- runner user/admin separation;
- outbound GitHub/package access;
- restart-after-power-failure and sleep settings;
- measured upload/download bandwidth;
- whether the host is dedicated or shared.

If it is shared with personal accounts or cannot isolate CI from personal credentials, stop: keep
hosted CI and revisit with dedicated hardware.
